# The GPU that was mostly waiting

About 60 minutes · 1 GPU · the slow baseline runs about 2 minutes, fixed runs take seconds

## The situation

A colleague's image classifier trains correctly and reaches good accuracy. It is also painfully slow, and they want to scale it up to a real dataset next month. Their plan is to "optimise the convolutions", because that's where the maths is. There's even a `TODO` in the code saying so.
Before anyone rewrites anything, you want to know where the time actually goes. Your job: use the agent to profile the script, find out what really dominates, fix it one change at a time, and measure each fix.
The script contains several deliberate performance mistakes, and one piece of misleading advice. Part of the exercise is finding out whether the agent follows the evidence or the comments.

## What you're given

All files are in the `materials/` folder:

```
material/
├── train_shapes.py  Trains a small CNN to tell circles, squares and crosses apart in noisy synthetic images. Prints time per step and test accuracy; --profile profiles 10 steady-state steps
└── RESULTS.md       The tables to fill in
```

The images are generated by the script itself, so there's nothing to download. The model, the data and the training settings (batch size 64, 400 steps) should stay the same throughout: the point is to make the same training faster, not to train less.

## Background

Asynchronous GPUs. When Python calls a GPU operation, PyTorch queues it and returns immediately; the GPU works through the queue in the background. The CPU only waits when it needs a result back, for example `.item()`, printing a tensor, or copying to the CPU. Each of these is a synchronisation point: the CPU stops until the GPU has finished everything queued so far.
The GPU can only be as busy as the CPU keeps it. In Python training loops, the CPU prepares every batch and launches every kernel. If preparing a batch takes longer than the GPU needs to process it, the GPU sits idle, however fast its convolutions are.
Profiling records how long each operation takes, on the CPU and on the GPU. `torch.profiler` gives a ranked table of operations, and a timeline (`trace.json`) that you can open in Perfetto to see gaps where the GPU waits. Profile steady-state steps only: the first steps include one-off setup.


## What to do

### Part 1 — Measure before you guess

1. Copy your job script from Exercise and change only the last line:

```
cd 08-slow-training
cp ../02-laptop-to-lumi/job.sh .
# last line of job.sh:
# srun singularity exec $SIF python3 train_shapes.py "$@"
git add . && git commit -m "baseline"
```

2. Submit two jobs: sbatch job.sh for the baseline timing and accuracy, and sbatch job.sh --profile for the profile. Fill in the baseline table in RESULTS.md.
3. Ask the agent to guess first. Start OpenCode and ask:

```
Read train_shapes.py. Without running anything and without any profile, which part do you expect to dominate the time per step, and roughly what fraction? Give a ranked list of your top three suspects.
```

Write its answer down. Did it follow the `TODO` comment?

### Part 2 — Let the evidence decide

4. Paste the profiler output into OpenCode:

```
Here is the profiler output from 10 steady-state steps on one LUMI GPU: <paste both tables> Using this profile and the code, rank the causes of the time per step. For each cause, quote the profile rows that support it, point to the lines in train_shapes.py responsible, and estimate the time per step after fixing it. Compare this with your earlier guess and say what changed. Don't change any files yet.
```

5. Check the agent's claims against the profile yourself. Look at the CPU table as well as the GPU one: if the biggest costs are CPU-side, which line of Python causes them? If you can, open `trace.json` in Perfetto: how much of each step is the GPU actually busy?

### Part 3 — Fix one thing at a time

6. Ask the agent to fix only the top-ranked cause:

```
Fix only the top-ranked cause. Keep the model, the data generation, the batch size, the number of steps and the augmentation's behaviour (random horizontal and vertical flips, extra noise with standard deviation 0.1) the same. Before saving, predict the new time per step. Save the file without asking.
```

7. Review the diff, commit it with a message naming the fix, submit `job.sh`, and record the agent's prediction, the measured time and the test accuracy in the fixes table.
8. Repeat steps 6–7 for the next causes, profiling again (`sbatch job.sh --profile`) whenever the ranking might have changed. Stop when a fix no longer makes a measurable difference.


## Done when

- the time per step is at least 20 times faster than the baseline, with the same model, data, batch size and number of steps,
- the test accuracy is within about 2 percentage points of the baseline,
- the fixes table has one row per change, each with a prediction and a measurement, and
- your paragraph in `RESULTS.md` says what dominated the time, how you knew, and whether the `TODO` comment was right.

## Going further

- Batch size sweep. With the fixes in place, try `--batch 16, 256 and 1024`. At which size does the GPU stop waiting for the CPU and start limiting the speed? Watch samples per second, not time per step.
- Mixed precision. Ask the agent to add `torch.autocast` with `bfloat16`. Which operations change in the profile, and does the accuracy survive?
- Compile it. Try `torch.compile(model)`. Does it help at this size, and what does the first step cost?
- Trick question for the agent: "Would switching this model to float64 make it much slower on LUMI's GPUs?" Check its answer against the MI250X specifications in the LUMI documentation: the right answer depends on the hardware, and many agents answer from experience with consumer GPUs.
